## 二、化简修复：修复前后实测

用真实规则引擎跑同一批表达式：

| 表达式 | 修复前 | 修复后 | 用到的新规则 |
|---|---|---|---|
| `1-(e-1)` | `1 - (e - 1)`（0 步） | `2 - e` | `SUB_NESTED_FOLD` |
| `-(e-1)` | `-(e - 1)`（0 步） | `1 - e` | `NEG_SUB` |
| `2-(e-1)` | 0 步 | `3 - e` | `SUB_NESTED_FOLD` |
| `1-(e-2)` | 0 步 | `3 - e` | `SUB_NESTED_FOLD` |
| `0-(e-1)` | 0 步 | `1 - e` | `SUB_NESTED_FOLD` |
| `2-(e+1)` | 0 步 | `1 - e` | `SUB_SUM_FOLD` |
| `-(1-e)` | 0 步 | `e - 1` | `NEG_SUB` |
| `2-(1-e)` | 0 步 | `1 + e` | `SUB_NESTED_FOLD` |
| `(e-1)-(e-2)` | 0 步 | `1` | `SUB_NESTED_SAME_LEFT` |
| `1-((e-1)-1)` | 0 步 | `3 - e` | `SUB_NESTED_FOLD`（两轮） |

**根因**：规则库只有匹配相同子式的特例（`a - (a - b) = b`），
缺少通用去括号规则，于是「被减数与内层不相等」的嵌套减法全部卡死。

**设计取舍**：折叠规则只在被减数与内层某一项同为整数时才改写。
全符号情形（`π - (i - e)`）改写后等长、并不更简，宁可不动 —— 否则只是污染化简步骤。
代价是少量漏网情形，已记入 [公式覆盖审计](公式覆盖审计.md)。

## 三、反向推导展示：真实浏览器验收（16/16）

在真实 Chromium 中按用户路径操作（点数值 → 点 `x`/`y` 槽位 → 添加），逐步构造出：

```
1  →  e  →  e^(e)  →  0  →  e - 1  →  e^(e - 1)  →  2 - e
```

| # | 验收项 | 实测 |
|---|---|---|
| 1 | 选中初始值 `1` 时只有一步并标明「初始值」 | 1 步 |
| 2 | 步数标注与步数一致 | 共 1 步 / 共 7 步 |
| 3 | `EML(1, 1) = e` | `e` |
| 4 | `EML(1, e) = e - 1` | `e - 1` |
| 5 | `EML(e, 1) = e^e`（化简掉 `ln(1)`） | `e^(e)` |
| 6 | `EML(1, e^e) = 0`（同项相消） | `0` |
| 7 | `EML(e - 1, 1)` 化简掉 `ln(1)` | `e^(e - 1)` |
| 8 | **`EML(0, e^(e-1))`：`1 - (e - 1)` 折叠为 `2 - e`** | `2 - e` |
| 9 | 推导过程列出完整链条 | 7 步 |
| 10 | 首步是初始值 `1` | ✓ |
| 11 | 末步是目标值并带「目标」标记 | `2 - e` 目标 |
| 12 | 复用值以「第 N 步」引用而非重复展开 | 12 处引用 |
| 13 | 末步输入正确指向 | `x = 0（第 4 步）· y = e^(e - 1)（第 6 步）` |
| 14 | 重新选中目标值仍展示完整链 | 7 步 |
| 15 | 重复添加同一公式不报错 | 提示「该数值和公式已经存在」 |
| 16 | 浏览器控制台无 error | 干净 |

### 一个需要说明的语义

推导链展示的是**依赖顺序**（先算输入、再算结果），不是用户的点击顺序。
上例中 `e - 1` 在第 ⑤ 步出现，虽然用户在第 2 次操作时就造出了它 ——
这是刻意的：链条回答的是「要得到目标，必须先有什么」。

## 六、CI 配置修复（本轮附带发现）

CI 工作流**自 2026-09-11 起连续 5 次失败**（v1.1.0 之后全部失败），
与本轮改动无关，是既存问题。

查下来是**两个独立根因叠在一起**：一个在测试步骤之前（缺一步生成），
一个在测试文件本身（模块系统混用）。只修前者会让 Node 22 变绿、
**Node 18 继续红** —— 第一轮修复（`bb8dce6`）正是这个结果：
失败面从「三个平台全红」缩成「只在 Node 18 红」，问题没消失，只是变窄了。

### 6.1 根因一：assets 是构建产物，CI 上不存在

`android/app/src/main/assets/` 是构建产物、被 `.gitignore` 排除，
CI 检出后该目录不存在；而测试里有一条断言「assets 与 dist 字节一致」（U03），
其中断言了 assets 存在 —— 于是 CI **必然**失败。

本地能过，是因为开发者自己 sync 过 assets —— **这个坑只在 CI 暴露**，
而失败信息看起来像「测试本身坏了」，掩盖了真实原因「少了一步生成」。

**修法**：`ci.yml` 在 `Run tests` 之前补上 `node scripts/sync-android-assets.mjs`，
并把 `npm run build` 提到最前（assets 同步依赖 dist 产物）。
顺带让 CI 真正校验这条不变量，而不只是本地有效。

**本地复现**：临时移除 assets 后跑测试，失败项**恰好只有** U03（110 pass / 1 fail），
与 CI 表现一致；恢复后 111/111 通过。

### 6.2 根因二：测试文件模块系统混用（只有 Node 18 能暴露）

`tests/android-shell.test.js` 是全仓**唯一**使用 ESM `import` 的测试文件，
另外 5 个都用 `require`；而 `package.json` 未声明 `"type"`，
`.js` 在 Node 下默认按 CommonJS 解析。Node 22 自带模块语法自动探测（20.19+ 起）
会照常加载，Node 18 没有这个能力 —— 于是直接语法错：

```
SyntaxError: Cannot use import statement outside a module
    at internalCompileFunction (node:internal/vm:76:18)
```

**性质与 6.1 完全一样**：本地跑 Node 22 永远看不见，只有 CI 的 Node 18 能发现。

这里有个决策需要说明：矩阵里的 Node 18 是 README 对外承诺的支持版本
（README 第 61 行「在 Node 18/20/22 上自动跑测试与构建」），
所以**不能靠删矩阵来变绿** —— 那等于把唯一能暴露此问题的环境关掉。
正确做法是让测试文件遵守仓库声明的模块系统。

**修法**：该文件改为 CommonJS（与其余 5 个测试文件一致）；
同时在 `ci.yml` 矩阵上方写明「测试文件必须 CJS，因为矩阵含 Node 18」，
把这条约束钉在它产生的地方，而不是只留一份说明文档。

**实证（下载 Node 18.20.8 本地复跑，不是推断）**：

| 对象 | Node 22.22.2 | Node 18.20.8 | Node 24.19.0 |
|---|---|---|---|
| 修复前（HEAD 版该文件） | 通过 | **SyntaxError，与 CI 日志逐字一致** | 通过 |
| 修复后（全量用例） | 111/111 | **111/111** | 111/111 |

同一宿主上「CI 日志里的报错」与「本地 Node 18 的报错」逐字相同，
可以确认复现的是同一个问题，而不是另一个碰巧相似的错误。

### 6.3 教训

两个根因是同一种形态：**失败信息都指向别处**。
6.1 看起来像「测试写坏了」，实际是「少了一步生成」；
6.2 看起来像「Node 18 不支持」，实际是「这个文件没跟其余 5 个保持一致」。
共同的规避手段是**把本地看不见的环境差异提前说出来** ——
6.2 的约束已写进 `ci.yml`，任何新增测试文件都会经过那行注释。
