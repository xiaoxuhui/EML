# 安卓打包方案（APK）

> 状态：**设计阶段** —— 方案已定稿，尚未开始编码。
> 创建日期：2026-09-06
> 适用版本：EML 计算台 v1.1.0

## 1. 目标与范围

把 EML 计算台打包成可在安卓设备上安装运行的 APK，目标是装在华为平板与手机上离线使用。

**已确认不在本次范围内：**

- 鸿蒙 HAP 原生包（见 §2 的决策依据）
- 上架应用市场
- 新增任何业务功能

## 2. 为什么只做 APK，不做鸿蒙 HAP

| 鸿蒙版本 | 内核基础 | 能否安装 APK |
|---|---|---|
| HarmonyOS 4.x 及以下（兼容版） | 基于 AOSP，双框架 | ✅ 能，APK 与 HAP 均可 |
| HarmonyOS 5.x / 6.x（NEXT 纯血版） | 鸿蒙微内核，已移除 AOSP 兼容层 | ❌ 完全不能，仅支持 HAP |

目标设备为华为 Mate 50 Pro，当前系统为 HarmonyOS 4.x，尚未升级，因此 **APK 路线即可覆盖**。

关于该机型未来能否升级到纯血鸿蒙，公开信息互相矛盾（部分页面称已列入 5.0 升级名单，另有引述官方适配计划称 Mate 50 / P60 系列不在名单内），不做断言。可确定的事实是：鸿蒙 5/6 的大版本升级走「我的华为 → 升级尝鲜」，**需用户手动确认，不会静默强推**。只要不主动升级，设备将长期停留在 4.x，APK 可持续使用。

若将来确需支持纯血鸿蒙，再按 §7 的预留路径补 HAP 即可。

## 3. 技术架构

EML 的构建产物 `dist/eml-workbench.html` 是**单文件自包含**（约 92KB，仅一个内联 script，无任何外链资源）。这一特性使安卓打包极其简单：原生壳只需把一个 HTML 文件塞进 `assets/` 即可，不需要处理资源目录、相对路径或跨域问题。

```
dist/eml-workbench.html          ← 唯一的网页资产（构建产物，已入库）
        │
        │  构建时同步（sync-web-assets）
        ▼
android/app/src/main/assets/     ← 同步产物，不入库
        │
        │  Gradle 构建
        ▼
APK  →  安卓设备 / 鸿蒙 4.x 设备
```

**壳的选型：极简 WebView 壳**（而非 Capacitor）。理由：

- 项目定位是 dependency-free 的纯静态工具，引入 Capacitor 会带来 `node_modules` 与插件体系，与仓库调性冲突
- 需求仅是「加载一个本地 HTML」，不需要原生插件能力
- 手写壳约 100 行 Kotlin，产物小、可控、可复现

## 4. 仓库结构与分支策略

```
main                        ← 稳定发布分支（v1.1.0 tag 在此，始终可发布）
│
├── feat/android-apk        ← 纯新增：android/ 目录 + GitHub Actions workflow
│
└── feat/touch-responsive   ← 改主应用：触摸拖拽 + 响应式布局
```

### 为什么拆成两个分支

| 维度 | `feat/android-apk` | `feat/touch-responsive` |
|---|---|---|
| 改动性质 | 仅新增目录与 workflow | 修改 `src/` 现有代码 |
| 是否触碰现有代码 | 否 | 是（`app.js` 拖放逻辑、CSS） |
| 是否影响桌面端 | 无 | 有，可能造成体验退化 |
| 风险等级 | 低（失败可直接删除目录） | 中高（需完整回归） |
| 验证方式 | 出包并安装到真机 | 83 项单元测试 + 浏览器实测 |

### 执行顺序

**先 `feat/android-apk`，再 `feat/touch-responsive`。**

先把「写代码 → 云构建 → 出 APK → 真机能装」这条链路跑通，尽早暴露 Gradle / SDK / 签名配置层面的问题——这类问题与业务代码无关，越晚发现成本越高。首个可用版本手感可以粗糙，只要能装能算即可；`touch-responsive` 随后优化交互并重新出包。

若顺序颠倒，会陷入「改了很久却仍不知道能否装到设备上」的风险敞口。

### 合并与提交约定

- 各自通过 PR 合并回 `main`，采用 squash merge
- 提交信息沿用仓库现有的 conventional commits 前缀：`feat:` / `fix:` / `docs:` / `release:`
- 合并前 `feat/touch-responsive` 需通过全部单元测试与浏览器实测

### `.gitignore` 追加项

```
android/app/build/
android/.gradle/
android/local.properties
android/app/src/main/assets/
*.apk
*.aab
```

同步生成的 assets 属于构建产物，不入库；每次构建时由同步脚本生成。

## 5. 构建方式：GitHub Actions 云构建

选择云构建而非本机构建，主要受磁盘约束：本机 C 盘仅剩约 12GB，而 JDK + Android SDK + Gradle 缓存需 8–15GB。云构建零磁盘占用，且可复现、产物可直接挂到 Release。

新增 `.github/workflows/android-apk.yml`，**仅在 `android/**` 发生变更或手动触发时运行**——Gradle 构建耗时较长，不应让每次 push 都触发。

签名策略：**先使用 debug 签名跑通流程**。debug 签名存在有效期且换机器安装会冲突，仅适用于验证阶段；若后续需要长期自用或分发，再生成正式 keystore 并改走环境变量注入（密码绝不写入仓库）。

## 6. 触摸与屏幕适配

这是本方案**唯一存在真实技术风险**的部分。

### 6.1 拖放交互（关键风险）

EML 当前使用 HTML5 拖放 API 实现「把数值块拖到 x / y 槽位」（`src/app.js` 的 `dragover` / `drop` / `dataTransfer`）。**该 API 在触摸端不会触发**，因此现有拖拽在手机和平板上完全失效。

好在代码中已存在触摸友好的回退路径：点击槽位即可将当前选中值赋给该槽位（`src/app.js` 的 `assignInput(slotName, state.selectedValueId)`），而 `click` 事件在触摸端正常触发。

三个候选方案：

| 方案 | 说明 | 评价 |
|---|---|---|
| ① 仅保留点击式赋值 | 触摸端隐藏拖拽引导，只用「选中 → 点槽位」 | 改动最小，但丢失拖拽手感 |
| ② 统一改为 Pointer Events | 鼠标与触摸共用一套拖拽代码 | **推荐**，两端体验一致，改动量中等 |
| ③ 长按拖拽模拟 | 用长按手势模拟拖放 | 体验花哨、代码脏，不推荐 |

### 6.2 响应式布局

EML 现有布局面向桌面多栏设计，手机竖屏会明显拥挤。

策略：**修改 EML 自身的 CSS，加入响应式断点**，一套网页适配所有尺寸，两个原生壳完全不需要参与布局。这样可避免维护两套页面。

需覆盖的形态：手机竖屏、手机横屏、平板竖屏、平板横屏。

### 6.3 其他移动端适配项

- WebView 需显式开启 `domStorage`（EML 用 `localStorage` 持久化数值与公式库）
- 禁用长按选择与文本选择放大镜
- 沉浸式状态栏、屏幕常亮
- 返回键处理（避免误触直接退出）
- 触摸目标尺寸不小于 44dp

## 7. 未来扩展：鸿蒙 HAP（暂不实施）

若将来需要支持 HarmonyOS 5.x / 6.x，路径如下，且与 APK 共用同一份 `dist`：

- 新增 `harmony/` 目录，ArkTS 工程，用 ArkWeb 的 `Web` 组件加载 `resource://rawfile/index.html`，资源置于 `entry/src/main/resources/rawfile/`
- 构建：`hvigorw assembleHap`
- **硬门槛（需用户本人完成）**：华为开发者联盟账号 + 实名认证；真机调试必须在 AppGallery Connect 申请 `.cer` 调试证书、注册设备 UDID、申请 `.p7b` Profile
- **建议本机 DevEco Studio（安装到 D 盘）**，而非 GitHub Actions——云端需自行配置数 GB 的 SDK 与环境变量，且证书与 Profile 属私密凭证

## 8. 版本与发布

- EML 当前版本 1.1.0
- APK 使用 `versionName 1.2.0` / `versionCode 2`
- `CHANGELOG.md` 同步记录
- 产物挂到 GitHub Release，或直接在设备上安装

## 9. 风险登记

| 风险 | 说明 | 应对 |
|---|---|---|
| HTML5 拖放在触摸端失效 | 现有拖拽在移动端不可用 | 采用方案 ② 改为 Pointer Events（见 §6.1） |
| 响应式改造影响桌面端 | 改 CSS 可能退化桌面体验 | 在 `feat/touch-responsive` 分支隔离，合并前完整回归 |
| Gradle / SDK 配置问题 | 云构建首次可能失败 | 先跑 `feat/android-apk`，尽早暴露 |
| debug 签名局限 | 有有效期，换机器装会冲突 | 验证阶段可接受，长期用需换正式 keystore |
| 鸿蒙未来升级 | 若设备升到 5.x，APK 失效 | 不主动升级即可规避；确需时按 §7 补 HAP |
