# 设计文档 — 反向推导展示（derivation-trace）

- **Status**：PENDING → 实现后转 COMPLETE → 浏览器验证后转 VERIFIED
- **Type**：feature
- **关联**：[需求与测试用例-反向推导.md](需求与测试用例-反向推导.md)

## 1. 现状与问题

每个数值已经完整记录了来源：`ValueRecord.derivationIds` → `Derivation`
（含 `xValueId` / `yValueId` / `directFormula` / `rewriteSteps`），
`Store.buildValueTree` 也能递归展开成**树**。

但树回答的是「这个值由什么组成」，不是「它是怎么一步步被造出来的」。
两者差别：

- **树**：同一数值在不同分支里会**重复展开**，且不体现先后顺序；
- **推导链**：线性、拓扑有序、每个中间结果只推导一次，后续引用其步号。

所以需要一个新的线性化视图，而不是把树拍平。

## 2. 方案选择

| 方案 | 做法 | 结论 |
|---|---|---|
| A | 新模块直接读 `state`，自行 DFS | **采用** |
| B | 复用 `buildValueTree` 结果做后序线性化 | 否决 |

否决 B 的原因：`buildValueTree` 产出的是**展开后的树**，同一个值在每个分支重复出现
（仅做环检测）。要在线性化时再去重，等于做两遍工作；而且它的截断语义是「深度/节点」，
与推导链需要的「步数」不是一回事。

采用 A，但**复用 `Store` 的预算常量风格**，保证两个视图对同一份数据的展开深度口径一致。

## 3. 数据结构

`src/derivation-trace.js`（UMD，与其他模块一致，浏览器挂 `EMLDerivationTrace`）：

```js
buildDerivationTrace(state, valueId, options) -> {
  ok: boolean,            // 是否完整（未截断）
  targetValueId: string,
  steps: Step[],          // 拓扑有序，末元素即目标
  truncated: boolean,
  reason: null | "step-limit" | "missing-value",
  extraSourceCount: number,  // 目标除首条来源外还有几条
}

Step = {
  index: 1,               // 1-based 步号
  valueId: string,
  displayText: string,
  kind: "initial" | "derived",
  // kind === "derived" 时：
  directFormula: string,
  rewriteSteps: Step[],
  x: Ref, y: Ref,
  // 目标步另有：
  isTarget: boolean,
}

Ref = { valueId, displayText, refIndex, kind: "initial" | "derived" }
```

## 4. 算法

**DFS 后序 + 已访问表**：

```
visit(id):
  若 firstIndex 已含 id        → 返回 { refIndex: firstIndex.get(id) }   // 复用，不重复展开
  若 inProgress 已含 id        → 返回环标记（防御性：正常数据不会出现）
  若步数已达预算               → 置 truncated，返回 deferred
  inProgress.add(id)
  d = 该值的第一条 derivation（若存在）
  若 d: x = visit(d.xValueId); y = visit(d.yValueId)
  push 步骤；firstIndex.set(id, steps.length)
  inProgress.delete(id)
  返回 { refIndex: steps.length }
```

后序保证：**任何值被 push 时，它的两个输入已经 push 完毕**，因此天然满足拓扑序（TR04）。

`firstIndex` 同时承担三件事：去重、复用引用、环的软处理。
`inProgress` 只用于防御真正的环（理论上 EML 只允许引用已存在的值，不应出现）。

## 5. 规模控制

- `MAX_TRACE_STEPS = 500`（推导链是线性视图，比树更省）
- 达到预算时**不静默截断**：`truncated: true` + 页面明确提示
- 与 `Store.MAX_TREE_NODES = 800` 分开：两个视图的粒度不同，共用会成为将来的耦合

## 6. 界面设计

「公式详情」面板在**「直接公式」与「完整计算树」之间**插入新板块「推导过程」。

理由：阅读顺序是「这个值是什么 → 怎么一步步来的 → 完整结构展开」，
线性时间线夹在中间比放在树后面更符合认知顺序。

渲染形态：

```
推导过程                                        共 3 步
─────────────────────────────────────────────────────
1  1                        初始值
2  e                        EML(1, 1)
   x = 1（第 1 步） · y = 1（第 1 步）
   ▸ 化简 2 步
3  e - 1                    EML(1, e)          ← 目标
   x = 1（第 1 步） · y = e（第 2 步）
   ▸ 化简 1 步
```

- 目标步加高亮与「目标」标记
- 初始值步不显示输入与化简
- 复用不会产生新步骤，只在输入行里体现为步号引用
- 截断时在列表末尾插入提示行
